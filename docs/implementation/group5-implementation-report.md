## 2. Implemented recovery persistence and transitions
Schedule-only manual alternatives now persist as private recovery CoordinationRecords with immutable ExecutionRevisions. A candidate PlanVersion is created inactive and retains its parent/context/digest. Proposal digest binds exact plan, issue/scope fingerprint, assumptions, risks, memory bundle and changed offers. States: pending â†’ approved/conditionally_approved, rejected, clarify or held; exact selected alternatives may become activated. Rejected/held records and original decisions remain in history. Failed feasibility returns deferred without mutating authoritative plan. Corrections use a new alternative, preserving the original. A hold explicitly remains non-activatable. There is no assertion that activation proves operational success; outcomes remain inconclusive.

Organizer APIs (all /v1/events/{event_id}): POST recovery/issues/{issue_id}/confirm; POST recovery/impact; GET/POST recovery/alternatives; POST recovery/alternatives/{id}/review; POST recovery/alternatives/{id}/activate; POST recovery/ai-runs. Participant APIs: GET recovery/offers/me; POST recovery/alternatives/{id}/assignments/{assignment_id}/consent. Mutations use existing authenticated event If-Match/idempotency/UoW boundaries. GET alternatives is organizer/private only. Own offers reveal only that participant's exact changed terms.

## 3. AI interface and actual execution
A RecoveryAdvice schema and provider-neutral recovery workflow use the existing AIRun/AIProposal/durable JobTask worker, bounded timeout/retry/fencing and pending human review. Inputs include current issue/scope fingerprint, confirmed/original context, real resource projection and current commitments, plus separate authorized historical memory. Typed alternatives cite supplied issue IDs, assumptions, risks, unknowns and conditions. Unknown work/completed/unrelated changes are rejected. Model output cannot activate anything; manual candidate creation and deterministic validation remain separate. No live adapter configured or live calls made. Model-request endpoint returns provider_unavailable without a configured adapter. A non-live adapter test exercises the worker; see final verification for actual pass/fail, not an inference from schema presence.

## 4. Deterministic validation
PlanContent validation and affected graph reject cycles/foreign references. Candidate schedules may alter only affected unfinished work. Validation checks stale plan/context/issue/work/assignment and resource fingerprints, exact retrieved-memory eligibility, dependency finish-to-start (including unchanged successors), stage windows, real on-hand stock and reservations, exact existing resource identity/units, accepted assignment state, applicant availability, schedule overlap, capability reviews, confirmed effort/capacity and pending consent/expiry/declines. Unsupported service/facility/funding/unknown supply stays conditional. No vehicles, permits, people, inventory or completed work are invented.

Important bounded limits: only schedule alternatives are implemented. Arbitrary splitting, changing resources/locations/roles, new governance evidence and general staff reassignment are not supported. Stage-window expansion requires another supported plan-design path. Capacity allocation is conservative; not a full resource-constrained optimizer. Cross-event availability needs clarification rather than assuming compatibility.

## 5. Atomic activation and reconfirmation
Changed accepted assignments receive inactive immutable AssignmentTerms with exact proposed schedule/work revisions and seven-day expiry. Existing accepted terms and authorization remain until activation; participant consent is stored in AssignmentConsent against that exact new digest. Silence, organizer approval and rejection are never consent. Withdrawn/changed/expired assignments block activation. Own acceptance/decline is authenticated and participant-locked.

Activation event-locks and revalidates plan, operational fingerprint, memory, resources, availability, consent, exact selected digest/revision and deterministic feasibility. It atomically switches changed terms, creates a coherent setup/finalization/publication, advances the authoritative plan, carries unchanged WorkExecution projections forward and preserves original records. Unchanged accepted terms are explicitly retained by the new publication; retained authority is valid only while that publication's plan is active. Existing reservations are rebased to the new plan without creating stock. Pending or conflicting conditions return deferred. Audit/outbox/source history is written using Group 4 primitives. Tests cover an actual commit, decline, stale issue, two activations racing and forced rollback; see final focused evidence.

## 6. Event Memory
Candidates use MuseSparkContextBuilder for event-only retrieval of eligible source-linked history, preserving current facts versus historical advice. Source/memory digests are bound and rechecked on review and activation. Successful and failed/inconclusive source-supported memories may be retrieved; no outcome is promoted. Recovery execution revisions flow through the existing source resolver/outbox and deterministic projection. Insight originals are excluded from generic source/memory retrieval. No cross-event private sharing or Modal inference.

Not delivered: a complete human evidence-backed recovery-success/failure outcome recording workflow. Activated, rejected and held alternatives remain proposed/attempted/inconclusive history, not fabricated generalized lessons.

Existing Join Event Additional Info renders enabled questions, reloads current private responses, saves exact configuration version and independent consent. Only the author reads raw answers through these APIs; aggregate consent does not authorize another participant or organizer to fetch originals. Organizer settings access before publication is authorized separately.
